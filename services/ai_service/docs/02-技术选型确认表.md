# 技术选型确认表（T4）

> 项目：小语手记·RAG 智能问答
> 约束：零预算 / 秋招三周时间 / 已有 Flask 主站（含机器人图标入口） / Windows 开发 + 虚拟机容器

---

## 决策 1：工程框架

| 候选 | 结论 | 理由 |
|---|---|---|
| **FastAPI 独立微服务（:8100）** | ✅ 选它 | 原生 async 适配流式/高并发 IO；与 Flask 主站解耦，互不影响发布；自动生成 OpenAPI 文档 |
| Flask 扩展（在主站加蓝图） | ❌ | 主站是同步框架，SSE 流式和异步调用会阻塞；AI 能力与博客发布节奏耦合 |
| Django | ❌ | 太重，ORM/Admin 对本项目无用；学习成本高，秋招时间不允许 |

**不选 Flask 扩展的原因**：手册要求 AI 能力独立成服务，主站零侵入，FastAPI 的异步能力是流式生成的前提。

**补充**：主站已有机器人图标入口，T17/T18 将在此基础上接入对话页与 SSE 代理。Flask 仅做网关（校验登录、注入身份、透传 SSE），RAG 链路全部由 FastAPI 承担，实现“在已有系统上零侵入扩展 AI 能力”。

---

## 决策 2：验证平台

| 候选 | 结论 | 理由 |
|---|---|---|
| **Dify 社区版** | ✅ 选它 | 可视化调参可测；插件生态全（Ollama/通义/硅基流动）；DSL 可导出版本化；免费 |
| 直接写代码验证 | ❌ | 效果差时不知道是检索、提示词还是模型问题，Debug 范围大 |
| LangFlow | ❌ | 生态不如 Dify 成熟，插件少；社区版功能受限 |

**不选直接写代码的原因**：新手最大的坑是“一上来就写代码，效果差不知道哪错了”。Dify 把链路可视化，每个环节单独可测。

---

## 决策 3：RAG 编码方式

| 候选 | 结论 | 理由 |
|---|---|---|
| **轻量自研 + 只用 langchain-text-splitters** | ✅ 选它 | 链路可控可讲；避免深栈调试；分块这种成熟轮子直接用 |
| LangChain 全家桶 | ❌ | 版本迭代快、抽象层深，出问题要读框架源码；面试讲不清“我到底做了什么” |

**不选 LangChain 全家桶的原因**：手册强调“代码级 Skill”——retriever.py、rerank_client.py、cache.py 每个模块单一职责，比框架黑盒更有说服力。

---

## 决策 4：向量库

| 候选 | 结论 | 理由 |
|---|---|---|
| **Qdrant** | ✅ 选它 | 单容器即起、payload 过滤强、REST + Python SDK 双全；已在本项目虚拟机 Docker 中运行 |
| Milvus | ❌ | 分布式架构重，依赖 etcd/MinIO，学生项目过度设计 |
| pgvector | ❌ | 需要引入 PostgreSQL 作为第二套数据库，与 MySQL 主库耦合、备份互相拖累 |
| FAISS | ❌ | 无持久化服务化、无元数据过滤，需要自己造数据库层 |

**不选 pgvector 的原因**：主站已有 MySQL，再引入 PostgreSQL 增加运维成本和数据同步复杂度。

---

## 决策 5：Embedding

| 候选 | 结论 | 理由 |
|---|---|---|
| **本地 Ollama bge-m3（1024d）** | ✅ 选它 | 批量调用零成本、隐私不出本机；Windows 有独显，速度足够；支持多语言和 8192 长文本 |
| 云端 bge-embedding | ❌ | 每次入库和提问都要付费，学生项目零预算不可持续 |
| 本地 bge-large-zh-v1.5 | ❌ | 仅中文、512 tokens，长文本需切更碎；bge-m3 更通用 |

**不选云端的原因**：Embedding 调用高频（入库几千条 + 每次提问一次），本地 GPU 边际成本为零。

---

## 决策 6：Rerank + LLM

| 候选 | 结论 | 理由 |
|---|---|---|
| **硅基流动 bge-reranker-v2-m3** | ✅ 选它 | 免费档即可支撑本项目流量；多语言、8K 长文本；Cross-Encoder 精排效果好 |
| 本地部署 Rerank | ❌ | 模型较大，本地跑成本高；硅基流动免费档足够 |
| **通义 qwen-plus（主）** | ✅ 选它 | 中文生成效果好、成本低；OpenAI 兼容协议，切换容易 |
| **DeepSeek deepseek-chat（备）** | ✅ 选它 | 主模型限流/超时时自动切换，保证可用性 |
| 本地 LLM（qwen2.5:7b） | ⚠️ 可选 | 质量不如云端，仅作最后兜底；本项目暂不启用 |

## 风险与边界（流量 ×100 还成立吗？）

| 决策 | 流量 ×100 后的风险 | 应对 |
|---|---|---|
| FastAPI 单实例 | 并发瓶颈 | 加 worker + Nginx 负载均衡 |
| Qdrant 单机 | 千万级向量后性能下降 | Qdrant 支持水平扩展，或迁移 Milvus |
| 本地 Ollama | GPU 显存不足，多 worker 冲突 | 降为 1 worker，或迁移 vLLM |
| 硅基流动免费档 | 限流 | 切换到付费档或备用 Rerank |
| 通义 qwen-plus | 成本上升 | 切换 DeepSeek 或本地 LLM 兜底 |
| Flask 网关 | 单点 | 主站可多实例 + Nginx 负载均衡 |

## 选型结论一句话总结

**Flask 主站（网关）+ FastAPI 微服务（RAG 链路）+ Dify（验证）+ Qdrant（向量库）+ 本地 bge-m3（召回）+ 硅基流动 bge-reranker-v2-m3（精排）+ 通义 qwen-plus / DeepSeek（生成）**，在零预算约束下构成完整 RAG 问答链路，月成本约 5-10 元。
